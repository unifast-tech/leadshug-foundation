## Merged Findings
### F-1DF50690 [high] Initial claim can authorize dispatch using eligibility observed before an authorization lock wait
- **Reviewers:** fresh-no-context-architecture-r4
- **Category:** `security`
- **Formalizable hint:** `yes`
- **Candidate rule level:** `project`
- **Candidate rule id:** `n/a`
- **Suggested action:** Arrange the claim so all potentially blocking authorization/lock acquisition precedes the final eligibility evaluation, pin mutable channel/credential inputs through claim commit, and evaluate the applicable trusted window using current database time at the final boundary. Coordinate the lock strategy with ARCH-ST04-R4-02. Add PostgreSQL barriers that hold the actor/grant lock, let the trusted window expire or rotate the credential version, then resume; require zero provider POSTs and no authoritative SENDING claim.
- **Rationale:** OutboundService.sendInitial's claim callback evaluates validateDispatchContext, including the trusted text window and credential version, before currentActorHasGrant executes FOR SHARE OF u, r, b. That authorization query can block. After it returns, claimInitial rechecks database time against only leaseExpiresAt and commits SENDING without reevaluating the window or credential tuple. A trusted window can expire during the wait while the 90-second lease remains live, allowing an official text POST outside the approved window. A credential-version change during the same interval also lacks a pinned credential row or final recheck. This violates D02/D04/D06 at the durable claim boundary. The existing expiry/revocation tests exercise other orderings; the embedded evidence does not demonstrate this ordering. Exploitability is source-supported and unexecuted here; the blast radius is an initial outbound operation in an authorized BU.

### F-7C61C9F4 [medium] Recent-attempt projection lacks an index supporting its bounded chronological lookup
- **Reviewers:** fresh-no-context-architecture-r4
- **Category:** `performance`
- **Formalizable hint:** `yes`
- **Candidate rule level:** `project`
- **Candidate rule id:** `n/a`
- **Suggested action:** Add narrowly scoped indexes supporting the actual recent-intent and applicable active-admission predicates and createdAt/id ordering, while retaining slot-uniqueness and quota indexes. Capture the emitted SQL and EXPLAIN ANALYZE with substantial released-attempt history and active-token fixtures; verify ordered bounded access rather than relying on returned-row counts.
- **Rationale:** InitialMessageService.options requests the latest 11 intents by createdAt/id for a conversation and BU. The supplied intent indexes do not support that ordering: the conversation index places slotReleasedAt and state before createdAt and omits the id tie-breaker. Consequently, LIMIT 11 bounds returned rows while PostgreSQL must examine and sort the conversation's accumulated attempt history. Released attempts are retained, so this work grows over time. Active ordinary-admission listing has a similar ordering mismatch when many tokens remain unreleased. The embedded EPS evidence covers inbox ordering, message existence and trusted-window projections, without a plan for these new recovery-history queries. This is a source/schema-supported access-path gap, without a measured outage claim.

### F-3119C7D6 [medium] Initial lifecycle transactions introduce a lock cycle with ST05 observation refresh
- **Reviewers:** fresh-no-context-architecture-r4
- **Category:** `structural_soundness`
- **Formalizable hint:** `yes`
- **Candidate rule level:** `project`
- **Candidate rule id:** `n/a`
- **Suggested action:** Remove the cycle through a bounded locking strategy compatible with the frozen identity/contact/conversation/intent ordering and protected ST05 behavior. Explicitly assess any needed protected-owner or approved-order change against renewed-approval requirements. Add a deterministic PostgreSQL overlap between actual observation refresh and initial claim/local completion, proving completion without deadlock, repeated provider dispatch or fabricated local success.
- **Rationale:** Initial claim and accepted local completion hold provider_resource_identities FOR SHARE before currentActorHasGrant requests shared locks on user, grant and BU rows. The preserved TemplateObservationService.ownsLease takes user/BU/grant/channel FOR UPDATE before requesting that same identity FOR UPDATE. A concurrent refresh can therefore hold the BU/user lock while waiting for the identity, as the initial transaction holds the identity while waiting for the BU/user lock. PostgreSQL must abort a participant. During accepted local completion this can unnecessarily leave a confirmed external send locally blocked. The cycle is directly supported by both embedded owners; its occurrence was not reproduced in this review. The blast radius is concurrent refresh and initial dispatch/completion for the shared official resource.
