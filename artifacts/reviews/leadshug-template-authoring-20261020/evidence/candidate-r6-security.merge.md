### F-9A1EDEE2 [medium] Successful GET parsing accepts contradictory Graph error envelopes
- **Reviewers:** fresh-internal-security-r6
- **Category:** `security`
- **Formalizable hint:** `yes`
- **Candidate rule level:** `project`
- **Candidate rule id:** `n/a`
- **Suggested action:** A) Recommended: reject top-level Graph errors and contradictory envelopes in the shared GET-object parser, retaining endpoint-specific shape validation. B) Apply equivalent explicit checks separately in listTemplates and getTemplate. C) Preserve current behavior only through renewed approval changing the fail-closed contract; do-nothing is not faithful to the existing baseline. Add raw HTTP tests for error plus empty data and error plus a valid APPROVED object. Verify that submission performs zero POSTs after contradictory preflight, while refresh preserves the previous observation as unavailable/ineligible and does not certify the contradictory status. Attribute this control to the embedded provider-trust requirements.
- **Rationale:** message-template.client.ts:225 readObject checks HTTP success and object shape but does not reject a top-level error. listTemplates at :106 therefore accepts HTTP 200 containing both data and error; data:[] can falsely establish name absence and permit the creation POST. getTemplate at :130 similarly accepts an otherwise valid APPROVED template accompanied by an error, allowing a contradictory response to become an eligible observation. Grant and creation parsing already reject comparable contradictions, so this is a gap in the GET boundary rather than a challenge to the approved refusal allowlist. No attacker-controlled Graph interception is established; exploitability depends on an inconsistent or compromised upstream response. Nevertheless, D05/D07 explicitly require inconclusive/error responses to fail closed. Existing raw tests cover contradictory debug-token and creation responses, not these GET cases.

### F-F8BF011A [medium] Sequential reconciliation bypasses provider-read throttling
- **Reviewers:** fresh-internal-security-r6
- **Category:** `residual_risk`
- **Formalizable hint:** `yes`
- **Candidate rule level:** `project`
- **Candidate rule id:** `n/a`
- **Suggested action:** A) Recommended: approve a narrow persistent recovery cooldown or read budget, enforced before provider I/O and coordinated for the affected operation/account. B) Record explicit nonblocking debt for the existing private cohort with an owner, containment and follow-up. C) Do nothing without a recorded disposition leaves the abuse path unassessed. Do not add background polling, workers or mutation retries. Verify with repeated sequential and concurrent reconcile requests against disposable PostgreSQL: provider GET counts remain bounded, throttled requests preserve the same ambiguous operation/reservation, and creation POST count never increases. Any material change to the recovery contract should follow TODO approval governance.
- **Rationale:** template-submission.service.ts:27-28 defines submission quota windows, but reconcile's AMBIGUOUS branch does not apply them or a separate recovery budget. claimReconciliation prevents overlapping recovery; releaseReconciliationLease immediately permits another request after a no-match result or ordinary provider failure. An authorized actor possessing one persistently ambiguous operation can repeatedly trigger a grant lookup and up to two filtered provider GETs, plus durable claim/release writes. This bypasses the ten-second debounce protecting observation refresh and can consume shared account/provider resources despite submission quotas. The attack is plausible from the source and has not been reproduced. OWASP API4 is directly relevant. D05 quotas govern submission, so this is a residual abuse-control gap requiring disposition, not an assertion that the approved submission limits were implemented incorrectly.

C) Leave unchanged only as an explicit security exception; the current package contains none. Add real-BFF/PostgreSQL held-response tests for both refresh routes: invalidate the session through passwordChangedAt or expire it before release, assert rejection, unchanged previous observation/page content and no newly eligible observation. Preserve historical submission receipts and avoid introducing another credential owner.
- **Rationale:** message-templates.controller.ts:126 and :145 invoke observation refresh without the captured-session revalidation supplied to submit and reconcile. A session valid at request entry can expire or be invalidated by a password change while the provider response is held, yet still persist current observations, mark APPROVED results eligible and return account content. This is a source-established path, not a reproduced exploit. The identity module explicitly requires grant/session revalidation after HTTP before promoting observations; no approved exception covers these new routes.
